# ADR 0003：迁移到 RimWorld 1.7，冻结 1.6 发布内容

1.7 是本 fork 后续开发、修复与运行验收的目标；1.6 是保留的上一版本，不再等待其运行环境来启动迁移。本 ADR 替代 [ADR 0001](0001-correctness-before-performance.md) 与 [ADR 0002](0002-work-attribution-and-direct-jobs.md) 中的“先通过真实 1.6 验收”要求，保留其账务、工作归属和先正确性后性能的约束。本文供迁移实施和发布验收使用；后续变更更新对应决定，不追加工作流水账。

## 决策时基线与实施状态

- 决策时项目为 `net48` / `Krafs.Rimworld.Ref 1.6.4633`，About 仅声明 1.6。现主线已切换 `net10.0` 与真实 1.7 引用，当前资源隔离到 `Common`；`1.6/Released` 保留原始完整资源。构建/加载/部署入口见 [README](../../README.md#构建与部署17)。
- #5–#8 的旧 37 项替身边界检查及设置几何探针只保留为历史证据；现已在真实 1.7 验证进食、原版归池/放置、NewRatkin driver、可用的卫生兼容和实际 UI，不把旧替身结果升级为游戏证据。
- 本次真实运行目标为 `1.7.4981 rev136`；API 参考为 `D:/References/Rimworld/Vanilla/1.7`。测试使用独立游戏目录和 profile，不修改玩家存档。Prison Labor 未加载进先前自动化 profile；用户随后确认个人生存档实测良好，后续性能批次保持其接管、派工和兼容对接不变。
- 邻近项目 [OhYouAreSoFast](../../../oh_you_are_so_fast/Source/OhYouAreSoFast.csproj) 已采用 `net10.0`、游戏根目录 `Assembly-CSharp.dll` / `UnityStubs.dll` 与 Harmony 3 的 1.7 程序集；沿用该构建与按版本加载的惯例。
- NewRatkinPlus 当前根 LoadFolders 的 1.7 分支选择根目录、普通 `1.6`、`1.7` 和内容/DLC 目录；其 1.7 工程编译普通 `1.6/Source`。此前核对的 `1.6/Released/1.6` 是旧版冻结内容，不是 1.7 driver 的证据。

## 决定

### 1. 单一维护目标，保留旧发布

- `Source` 切换为只构建 1.7 的 `net10.0` 项目。删除旧版编译引用和机器相关复制路径，不为仅保留的 1.6 发布版维护第二套源码分支、条件编译或双目标框架。
- 保留 MIT、上游署名、程序集名和现有持久化类型/字段标识。迁移初期沿用上游包名；2.5.0 按维护者要求切换为 `nanaloveyuki.prisonerspaytoeat2.fork`，并声明与 `AAA.PrisonersPayToEat2` 互斥。启用列表需手动换为 fork；现有存档内的类型及字段不改名。版本与支持声明明确区分上游 1.6 发布和本 fork 的 1.7 更新。
- 1.6 冻结的是**完整加载内容**，不仅是 DLL：从 vendor commit `8539fff` 还原当时使用的 Defs、Patches、Languages、Textures，并在迁移时隔离为旧版资源快照。不能把工作区已改的共享设置文案当成旧发布原件。
- 原 `1.6/Assemblies/PrisonersPayToEat2.dll` 原样保留，不重编、不回填 #5–#8 修复；预期 SHA-256 为 `1885eeee58107c13067322562fdc55c3c9304b216d9c8a7a66fbc07422a85fa9`。1.6 保留既有缺陷，不声称获得本轮修复或新的验收保证。
- 不承诺将 1.6 游戏存档转换为 1.7；跨游戏版本存档能否打开由游戏自身支持决定。可由 1.7 正常打开的存档及沿用的模组设置，按下述持久化约束验收。

### 2. 构建与加载彻底按版本隔离

- 构建显式引用本机 1.7 游戏根目录实现程序集和 `HarmonyAssemblyPath` 指向的 1.7 Harmony 3；`RimWorldDir`、`HarmonyAssemblyPath` 沿用仓库的环境变量/属性配置约定。缺失或版本不匹配应在构建检查处明确失败，不回退到 RimRef 1.6。
- 程序集输出为 `1.7/Assemblies/PrisonersPayToEat2.dll`，游戏和 Harmony DLL 均不随本 Mod 复制。需要的 Waylith 相关引用以实际 API 使用为准，不预先引入所有依赖。
- 新增显式 LoadFolders：1.6 仅加载冻结资源与原 1.6 程序集；1.7 仅加载当前资源与 1.7 程序集。旧版资源可置于 `1.6/Released`，当前资源集中于 `Common`，遵循邻近项目布局；根目录不再作为隐式“两个版本共用一切”的入口。
- 每个版本的 Defs、Patches、语言、纹理及程序集只加载一次，1.7 不加载旧版 DLL。About 支持声明保留 1.6，并在 1.7 实现和加载验证通过后增加 1.7。
- 后续接入 `scripts/deploy` 的标准模块入口。build-only 只编译/暂存；正式部署保留目标 `PublishedFileId.txt` 和旧版内容，使用仓库既有运行中保护。升级部署与全新部署均验证加载目录，不手工覆盖正在运行的游戏。

### 3. 迁移全部现有功能，不夹带经济规则重写

迁移覆盖本模块全部生产路径：找食与进食、账户/儿童代付/借款、时薪及各类计件、赎身与社会行为、囚犯需求和健康状态、内置劳工/区域/账单限制/日程/服装、通讯台索要、娱乐、卫生兼容以及所有设置和管理 UI。不以移除设置、跳过补丁或吞掉异常来换取启动成功。

- 对每个 Harmony 目标核对 1.7 的方法签名、重载、字段访问和实际调用位置；兼容性补丁仍在 Defs 可用后安装。初始化成功不等于热点调用已经进入补丁，必须观察实际调用结果。
- 重新核对 Job 清理/归池顺序、搬运成功语义、进食实际份数、研究贡献口径与 UI 集合/迭代器契约；迁移 #5–#8 修复，不能机械套用 1.6 行号或对象生命周期。
- NewRatkinPlus 按实际 1.7 加载的 Defs 和 driver 核对两条派工来源、工作完成与娱乐入口。现有“两段 toil、4000 tick、索引 2”只是 1.6 实现事实；在 1.7 得到证据前不沿用为结算断言。继续原生来源优先、精确适配、未知不猜测、不篡改第三方 Job。
- Prison Labor、Dubs Bad Hygiene 等软依赖分别记录 1.7 实际可用版本与证据。依赖缺席时基础功能正常；依赖存在时验证适配，不把“未加载依赖”写成“兼容已通过”。若目标没有可用 1.7 版本，在对应 issue 记录缺失条件和明确的支持范围，不伪造兼容或静默降级。
- 保持即时余额、自动还债顺序、倍率与个体覆盖、派工许可和工作归属分离、专用/通用计件互斥，以及身份/离图/读档的遗留清理。性能改动仍单独实施。

### 4. 持久化保持连续，临时状态按新运行时重建

保留现有 Scribe 键、枚举数值、Def 名、账户索引和可序列化类型身份。用 1.7 新档保存再读取，并对游戏能够打开的既有模组数据验证余额、借款、赎身状态、个体设置、真实工种键、劳作区和账单权限不丢失。发现格式确需变化时，先记录具体迁移规则，再实现；不无故重命名或初始化覆盖。工资/研究贡献、娱乐/战斗会话等临时状态沿用明确的清理与重建策略，禁止跨存档残留。

## 实施次序与放行条件

| 阶段 | 完成条件 |
| --- | --- |
| 1. 隔离与编译迁移 | 冻结完整 1.6 发布；net10.0 引用、LoadFolders、元数据和部署配置一致；完整项目编译通过；旧版 DLL/资源内容比对通过 |
| 2. 1.7 加载与功能适配 | 真实 1.7 启动并加载全部 Defs/补丁；实际设置、管理 UI 和囚犯行为可观察；全部现有功能和软依赖支持情况有证据，不只证明启动无异常 |
| 3. 正确性回归 | 在真实 1.7 或其真实实现程序集上覆盖 #5 免费/强制收费/实际份数/赊账，#6 真实清理归池/不归池/池满/连续任务，#7 真实放置失败→重试成功；#8 两条发电来源、模式覆盖、完整会话与中断；检查即时余额、还债、身份变化、离图和存读档。游戏内观察发电状态和饭票变化，UI 必须有视觉证据 |
| 4. 部署与 issue 收口 | 通过标准入口 build-only 后部署，核对实际加载的 1.7 DLL 和资源、目标 Workshop ID 保留以及 1.6 内容未被覆盖；#5–#8 以 1.7 验收结果收口，明确旧 1.6 未回填修复 |
| 5. 性能批次 | 1.7 正确性门禁通过后，执行 ADR 0001 的扫描、分配与零囚犯休眠方案；同一 1.7 场景采集前后数据，不拿 1.6 探针次数冒充 1.7 收益 |

不再要求恢复真实 1.6 游戏才能开展或完成 1.7 迁移。1.6 只做发布内容保全检查；缺少真实 1.7 依赖、运行路径或存档证据时，阻塞的是相应的 1.7 验收，不重新退回 1.6 门禁。

## 取舍

- 不继续双版本源码维护：保留旧发布比维护两套 CLR/API 更简单，代价是旧版缺陷不回填。
- 不先优化再适配：更换运行时和 Harmony 调用路径已经改变性能基线，先验证经济与派工语义，才能区分迁移回归与优化收益。
- 不只改支持版本和目标框架：编译不能证明补丁被实际调用，更不能证明工资、存档和第三方直接派工正确。
